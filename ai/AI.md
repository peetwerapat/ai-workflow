# AI Working Agreement (Global)

The **shared rules** for every project and every assistant (Claude Code / Codex CLI / Antigravity CLI / ZCode).
Each project has its own context in `.ai/` — always read every layer that exists.

> **Language**: always talk to the dev in **Thai** (technical terms may stay English). These instruction files are English only to save tokens — see [Output Language](#output-language).

---

## Context Layers

| Layer | Location | Owner | Content |
|---|---|---|---|
| **Global** (this file) | `~/.ai/AI.md` | shared by all projects | workflow, commands, rules that apply everywhere |
| **Project shared** (optional — multi-repo) | `<project>/.ai/context/` containing `PROJECT.md` | per project (many repos) | system overview, domain, shared conventions, contracts between repos, cross-repo ADRs |
| **Repository** | `.ai/` in the repo + memory file at root | per repo | tech stack, architecture, specs of that repo |

A standalone repo (not in a multi-repo project) has only Global + Repository, as before.

**Project memory file** = the file each assistant auto-loads from the repo root
- Claude Code → `CLAUDE.md`
- Codex CLI → `AGENTS.md`
- Antigravity CLI (`agy`) → `AGENTS.md` or `GEMINI.md` (reads both, walking up from cwd to the repo root)
- ZCode → `AGENTS.md` (or `.zcode/AGENTS.md` / `.agents/AGENTS.md`)

> Any of the 3 files in a repo counts as the same project memory — read whichever exists.
> **`.ai/context/MEMORY.md`** (if present) = this machine's personal memory, used when the team already tracks the memory file (team files are off-limits).
> Always read it **after** the team memory file — on conflict the team file wins; flag it to the dev.
> Repo has no `.ai/` yet → suggest the dev runs `/ai-init`.

## Project Layout (shared convention)

```
<repo>/
├── CLAUDE.md | AGENTS.md | GEMINI.md   # project memory (root, auto-loaded) — read-only if tracked by the team
└── .ai/
    └── context/
        ├── MEMORY.md         # (optional) personal memory — only when the team tracks the memory file
        ├── ARCHITECTURE.md   # ADRs, patterns, anti-patterns
        ├── features.md       # derived index — regenerated by /reindex only
        ├── untracked.md      # shared infra not counted as features
        └── specs/
            ├── TASK-YYYYMMDD-HHMM.md          # active
            └── CLOSED-TASK-YYYYMMDD-HHMM.md   # terminal status
```

### Multi-Repository Project (optional)

A project with several git repos (any number, any names) can share project-level context:

```
<project>/                     # need not be a git repo
├── .ai/context/               # shared — source of truth for cross-repo matters
│   ├── PROJECT.md             # marker + repo list + domain + context map (read on every task)
│   ├── ARCHITECTURE.md        # system overview + cross-repo ADRs (P-ADR-NNN)
│   ├── conventions.md         # conventions identical across repos
│   ├── integrations.md        # contracts between repos (API / event / shared data)
│   ├── features.md            # index of cross-repo tasks — regenerated by /reindex
│   └── specs/                 # cross-repo specs only (tasks touching ≥ 2 repos)
├── <repo-a>/.ai/context/      # normal repo layout (above) — repo-a only
└── <repo-b>/.ai/context/
```

Created by `/ai-init` at the project root (auto-detected, or `/ai-init --project`) — produces shared + `.ai/` for every detected repo.
`/ai-init` in a single repo (or `--repo`) = original behavior; if shared context exists above, it references it instead of copying.

### Context Resolution (every command / every assistant)

1. **Find shared context**: walk up from the current repo root one level at a time — the first `<dir>/.ai/context/PROJECT.md` found = the project's shared context
   - Not found → standalone repo, use only the repo's `.ai/` (original behavior)
   - cwd is the project root itself (not a repo) → read `PROJECT.md`, then pick repos by task
2. **Load only what is needed** (token saving):
   - `PROJECT.md` always → other shared files per the Context Map in `PROJECT.md`
   - `.ai/` of **repos the task touches only** — ❌ never load context of unrelated repos
   - cross-repo task → shared + `.ai/` of each involved repo + source code of those repos
3. **No duplication**: anything already in shared must not be copied into `<repo>/.ai/` or the repo memory file — reference the path instead.
   On conflict → repo-level wins for that repo, but flag to the dev that shared is out of date.

### Cross-repo Task (task touching ≥ 2 repos — any number)

- **One spec file** at `<project>/.ai/context/specs/TASK-*.md` — business rules written once. ❌ Never split into duplicate specs per repo
- Header has `**Scope**: cross-repo` + `**Repos**: {repo}, {repo}, ...` (in **build order** — provider before consumer)
- Proposed Design / Implementation Status **per repo** — every path prefixed with the repo name (`api/src/...`)
- **Overall Status** derived from per-repo status: any 🔴 → 🔴 · any 🚧 or (📋 mixed with ✅/⚠️) → 🚧 · ✅ in every repo → ✅ · all done but some ⚠️ → ⚠️ · 📋 in every repo → 📋
  (❌ / 📦 are set at task level only, via `/change --cancel / --deprecate`)
- **Open the session at the project root** to `/build` / `/change` several repos — some assistants (e.g. Codex sandbox) can only write inside the opened directory
  or `/build <task-id> --repo <name>` one repo at a time from a session in that repo
- Always commit per repo (separate git repos) — put `Task: {task-id}` in the message for cross-repo traceability

**Finding a spec by task-id** (every command): current repo's `.ai/context/specs/` → `<project>/.ai/context/specs/` (both `TASK-` and `CLOSED-TASK-`)
At the project root: `<project>/.ai/context/specs/` → each repo's `.ai/context/specs/`

**`.ai/` is shared by every assistant** — never split into `.claude/context/`, `.codex/context/`, etc.
One spec set, no drift.

**`.ai/` + memory file are local-only to this machine (default)** — `/ai-init` adds the memory file + `.ai/` to the work repo's `.git/info/exclude` → nothing to commit, and ❌ never commit/push them (files stay; git just doesn't see them).
To share with the team: the dev removes those lines from `.git/info/exclude` and commits.

## Development Workflow

Use these slash commands — do not skip steps.

| Command | Use when |
|---|---|
| `/ai-init [--project\|--repo] [--lang en\|th]` | new repo / multi-repo project without `.ai/` → scaffold context + project memory |
| `/spec <requirement>` | new requirement → analyze + save spec |
| `/build [task-id]` | implement per spec + write tests |
| `/change <task-id> "<desc>"` | modify an existing feature (bug / requirement change / refactor) |
| `/status [filter]` | feature overview |
| `/reindex [--force]` | regenerate `features.md` from `specs/` + auto-close terminal tasks |
| `/sync [--fix]` | detect drift between specs ↔ real code |

### Standard Flows

```
New repo:      /ai-init → /spec
Multi-repo:    cd <project> && /ai-init --project
Cross-repo:    cd <project> && /spec → /build (repo by repo in build order) → /reindex
New feature:   /spec → confirm → /build → /reindex → review
Modify:        /change → confirm → auto-apply → /reindex
Urgent bug:    /change <task-id> "bug: <desc>"
Daily start:   /status mine
Weekly check:  /sync → /reindex
```

### Flags

- `--quick` (spec / change) — skip analysis, trust dev
- `--incremental` (build) — stop for review after every layer
- `--no-test` (build) — skip tests (prototypes only)
- `--resume` (build) — continue where it stopped
- `--dry-run` (change) — show impact without changing anything
- `--fix` (sync) — fix detected drift
- `--force` (reindex) — re-read closed specs

> ⚠️ **Never `--quick` for**: auth, payment, money/point/tier calculation, multi-tenant isolation, data migration.
> These always get full analysis even if the dev passes `--quick` — warn, then do the full analysis.

## Status Vocabulary

One set for every project, in spec files and `features.md`.

| Icon | Status | Meaning | Terminal? |
|---|---|---|---|
| 📋 | Planned | spec exists, not built | — |
| 🚧 | In Progress | being built / stalled | — |
| ⚠️ | Done (untested) | built without tests | — |
| ✅ | Done | built + tests pass | ✔ |
| 🔴 | Blocked | has a blocker | — |
| ❌ | Cancelled | cancelled | ✔ |
| 📦 | Deprecated | no longer used | ✔ |

**Terminal** = `/reindex` auto-renames the file to `CLOSED-TASK-*.md`.

**Task ID**: `TASK-YYYYMMDD-HHMM` (created only when the spec is finalized)
**Revision ID**: `{task-id}-R{NN}` (incremented on every successful `/change`)

## Ownership Rules (who may edit what)

| File | Writable by | Never touched by |
|---|---|---|
| `specs/TASK-*.md` (spec content) | `/spec`, `/change` | `/build`, `/status`, `/reindex` |
| `specs/TASK-*.md` (Status / Implementation Status / Changelog / Gotchas) | `/build`, `/change`, `/sync --fix` | `/status` |
| `features.md` | `/reindex` only | every other command |
| `ARCHITECTURE.md` | dev (AI may propose, dev must confirm) | — |
| memory file tracked in git (team's) | dev / team only — AI may propose a diff | **every command**, including `/ai-init --force` |
| `.ai/context/MEMORY.md` | `/ai-init`, dev | — |
| `<project>/.ai/context/{PROJECT,ARCHITECTURE,conventions,integrations}.md` (shared) | `/ai-init` (first time), dev — other commands may propose a diff; dev must confirm before writing | `/status`, `/reindex` |
| `<project>/.ai/context/specs/`, `features.md` | same rules as the repo's `specs/` + `features.md` (above) | — |
| source code | `/build`, `/change` | `/spec`, `/status`, `/reindex`, `/sync` (except `--fix`, which edits docs) |

> `features.md` is a **derived view**, not a source of truth — the source of truth is `specs/`.

## Critical Rules (every project)

### 1. No spec = no implementation

- New features always go through `/spec` first
- Dev asks to change a business rule directly → recommend `/change` for an audit trail
- Trivial work (typo, log message, formatting) → just do it, no spec

### 2. Always read context before writing code

Order: shared project context (if any — see Context Resolution) → project memory (root) → `.ai/context/MEMORY.md` (if any) → `.ai/context/ARCHITECTURE.md` → spec file → module rule (if any) → real code

### 3. Follow existing patterns

- Look at surrounding code first — match naming, layering, error handling, test style
- Found a pattern not in `ARCHITECTURE.md` → tell the dev an ADR should be added (never add it yourself)
- ❌ Never introduce a new style because you think it is better

### 4. Multi-tenant isolation (if the project is multi-tenant)

- Every query filters by a tenant key derived from the **authenticated context** only
- ❌ Never trust a tenant key from query / body / header
- Cross-tenant access → return 404, not 403 (hide existence)
- Unsure whether a query needs the filter → **ask first, never guess**

### 5. Security

- ❌ Never hardcode secrets / credentials / API keys — always read from config or env
- ❌ Never read or print the contents of `.env`, `*.pem`, `*.key`, `secrets/`
- ❌ Never commit / push automatically — the dev reviews and commits
- ❌ Never run destructive commands (`rm -rf`, `DROP`, force push, `git reset --hard`) without confirmation

### 6. Test

- `/build` and `/change` always come with tests, except `--no-test`
- Tests fail 3 times → **stop** and report; leaving 🚧 beats a fake ✅
- REFACTORED → existing tests must pass unchanged; if they break, it is not a real refactor

### 7. Migration / schema change

- Never hand-create migration files or timestamps — always generate via the project's CLI
- Must be reversible (up/down); never edit a migration that is already merged

### 8. New dependency

- Always flag + ask the dev to confirm before installing
- Explain why existing ones cannot be used

## Subagents

`/spec` and `/change` delegate analysis to a separate agent to save main context.

| Agent | Used by | Job |
|---|---|---|
| `spec-analyzer` | `/spec` | requirement → business rules / risks / edge cases / design |
| `impact-analyzer` | `/change` | change request → conflict check / dependency trace / risk / approach |

**Runtime supports subagents** (e.g. Claude Code: Task tool) → delegate
**Not supported** (e.g. Codex CLI) → read `~/.ai/agents/{agent}.md` and follow it yourself in one focused pass
Both paths must produce the same result.

## Output Language

- **Talk to the dev in Thai** (English technical terms are fine) — even though these instruction files are English
- **Code / code comments / commit messages / branch names** → always English
- **Spec files**: business rules / edge cases → Thai; technical terms + paths + code → English
- **Original requirement** in a spec → preserved in the language the dev typed
- **Context files** (memory file, `MEMORY.md`, `ARCHITECTURE.md`, `untracked.md`, `PROJECT.md`, `conventions.md`, `integrations.md`): language chosen at `/ai-init --lang en|th` (default `en`)
  — when editing an existing context file, write in **that file's existing language**
- Commit message format: `{type}({scope}): {description}` (conventional commits)

---

## Working Style

1. **Unsure → ask**, rather than assume and fix later
2. **Report every assumption** made because the spec was unclear
3. **Point out what needs review** — spots that need human judgment
4. **Do not expand scope** — do what was asked; flag other problems instead of fixing them
5. **Unfinished means say unfinished** — never report done while tests fail
